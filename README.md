# CS-255-System-Analysis-and-Design
# Briefly summarize the DriverPass project. Who was the client? What type of system did they want you to design?
The DriverPass project was all about creating a user-friendly, cloud-based platform for driving education. The main goal was to tackle the issue of a super high DMV test failure rate—over 65%. To help students prepare better, the client wanted a system that combined everything: different user accounts for students, instructors, and admins, online training modules that run automatically, and a scheduling system for behind-the-wheel sessions that updates in real time.
# What did you do particularly well?
I managed to break down some unclear client interview notes into clear Business Requirements Documents (BRDs). I also mapped out the business rules into organized UML Diagrams, making sure everything lined up well between user roles and the scheduling database.
# If you could choose one part of your work on these documents to revise, what would you pick? How would you improve it?
I think it would be great if I got to refine the architecture a bit. Maybe I could have included some explicit data validation loops for processing payments. Also, having clear parameters for real-time database responses between the user front-end and the cloud layer could really enhance the system.
# How did you interpret the user’s needs and implement them into your system design? Why is it so important to consider the user’s needs when designing?
I grouped system requirements by role to align with how users actually behave. For example, students got easy-to-use calendar layouts and quick feedback on tests, while administrators had access to high-level data dashboards. It's super important to design with user needs in mind because it boosts engagement, cuts down on training time, and helps avoid costly rewrites after launch.
# How do you approach designing software? What techniques or strategies would you use in the future to analyze and design a system?
My approach utilizes a strict Requirements-First Approach. This means I get all the data flows, non-functional requirements, and security stuff sorted out before diving into coding. In future projects, I'm planning to weave in some Threat Modeling to automate compliance and security reviews right from the start. I also want to use Agile User Stories to capture requirements directly from the user's viewpoint, so everything stays relevant and on point.
